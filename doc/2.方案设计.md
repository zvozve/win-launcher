# WinLauncher 方案设计

> 需求来源：`doc/1.开发需求,md`
> 技术栈：**Qt 6.8.3 + MSVC2022 Build Tools 64bit + Ninja**
> 形态：**弹出式面板**（macOS 26/27 的 Spotlight「应用程序」浮层），不是旧版全屏启动台

---

## 0. 一句话目标

按热键弹出一块圆角毛玻璃面板：顶部搜索栏、下方图标网格；自动读取系统已安装软件；支持拖入 `.lnk` 添加；独立的编辑窗口增删图标与改设置。

## 2. 架构选型（已定）

| 决策 | 结论 | 理由 |
|---|---|---|
| UI 层 | **QML 界面 + C++ 后端** | 毛玻璃/缩放动画/自由拖拽是 QML 舒适区；扫注册表、解析 lnk、激活 UWP 是 Win32/COM 的活 |
| 扫描范围 | **开始菜单 + 注册表 Uninstall** | 只扫开始菜单漏免安装程序；全盘索引噪音太大 |
| 图标 | **`SHGetImageList(SHIL_JUMBO)` 256px → 缓存 PNG** | `QFileIconProvider` 多数只有 32/48，会糊 |
| 毛玻璃 | Win11 `DWMWA_SYSTEMBACKDROP_TYPE = DWMSBT_TRANSIENTWINDOW`；Win10 退回 `SetWindowCompositionAttribute` 丙烯酸 | 兼容性 + 效果双保 |
| 构建器 | **Ninja（单配置）+ 每配置独立构建目录** | 见 §5 |

## 3. 代码结构

与 `icloud-mon` 保持同一套约定：头文件 `inc/`、实现 `src/`、QML `ui/`，三者都在 target
sources 里显式列出；QML 走 `resources/*.qrc` + AUTORCC（不是 `qt_add_qml_module`）。

```
win-launcher/
├── CMakeLists.txt              单目标 WinLauncher；AUTOMOC + AUTORCC
├── build.bat                   一键：MSVC env → cmake → build → windeployqt
├── readme.md
├── doc/                       1.开发需求 / 2.方案设计
├── inc/                        12 个头文件（平铺）
│   ├── AppItem.h              条目数据单元（QObject，暴露给 QML）
│   ├── AppScanner.h           buildTasks() 枚举 + runTask() 解析（**都在 GUI 线程**）
│   ├── BackdropBlur.h         抓屏 + 模糊 + 提饱和 + 圆角 + 外阴影（自绘玻璃底图）
│   ├── BackdropProvider.h     image://wlbg/ 把底图交给 QML
│   ├── ShortcutResolver.h     IShellLink 解析 .lnk / .url
│   ├── IconProvider.h         256px 图标提取 + 缓存 + 归一化
│   ├── Launcher.h             启动：ShellExecute / QProcess / AUMID 激活
│   ├── WindowEffects.h        DWM 材质 / 圆形区域 / 深色 / 隐藏任务栏图标
│   ├── LauncherWindow.h       QQuickWindow 子类：弹出定位 + 圆角 + Esc/失焦收起 + 热键消息
│   ├── HotkeyManager.h        RegisterHotKey + 序列解析 + 失败回滚
│   ├── Config.h               config.json / 注册表自启 / 系统深色 / **搜索类型表**
│   ├── EverythingSearch.h     Everything SDK 动态加载（全盘搜索源）
│   ├── DebugTrace.h           `--trace` 打点写文件
│   └── Controller.h           前后端唯一门面，QML 里叫 `Ctrl`
├── src/                        同名 .cpp + main.cpp
├── ui/                         12 个 QML（平铺）
│   ├── Main.qml               根窗口 = LauncherWindow
│   ├── LauncherPanel.qml      搜索栏 + 网格 + 状态行
│   ├── SearchBar.qml          类型选择 + 放大镜 + 输入 + 清空 + 搜索源
│   ├── CategorySelector.qml   搜索类型下拉（应用/文档/图片/视频/音乐/压缩包/全部）
│   ├── EditWindow.qml         编辑窗口：只做图标增删（不透明）
│   ├── SettingsWindow.qml     设置窗口：只有设置项（不透明）
│   └── AppTile / GlassPanel / PillButton / SectionTitle / SettingRow / HotkeyRecorder
├── resources/winlauncher.qrc   QML 打进 exe，引擎用 qrc:/qml/Main.qml 加载
├── packaging/
│   ├── deploy.bat              windeployqt + 补拷 Everything64.dll
│   └── fetch-everything-sdk.bat
├── third_party/everything/     SDK DLL（不入库）
└── build/
    ├── Debug/WinLauncher.exe
    └── Release/WinLauncher.exe
```

数据流单向：`AppScanner → Controller → QML`；编辑动作 `QML → Controller → Config/layout.json`。


## 4. 关键技术点

| 主题 | 做法 |
|---|---|
| 弹出定位 | 取 `QCursor::pos()` 所在屏幕，尺寸按屏幕比例算（宽 62% 夹在 760–1280，高 66% 夹在 480–900），居中且上移 1/12 屏高 |
| 窗口 | `FramelessWindowHint \| NoDropShadowWindowHint` + `setColor(transparent)` + `WS_EX_TOOLWINDOW`（不进任务栏）+ 置顶 |
| 收起 | Esc / 失焦（可关）/ 工具栏「关闭」 |
| 全局热键 | `RegisterHotKey` 注册到窗口 HWND，`WM_HOTKEY` 从 `LauncherWindow::nativeEvent` 转给 `HotkeyManager`；改键失败自动回滚 |
| 单实例 | `QLocalServer` 命名管道，二次启动唤起已有实例 |
| 自启 | `HKCU\...\CurrentVersion\Run`，值为 `"exe" --autostart`；启动时以注册表为准 |
| 启动顺序 | **先建引擎/显示窗口，扫描用 `QTimer::singleShot(300ms)` 延后**（原因见 §7.1） |
| 配置 | `%LOCALAPPDATA%\WinLauncher\config.json` + `layout.json`（手动条目）；图标缓存 `%LOCALAPPDATA%\WinLauncher\cache\icons` |
| 排查 | `WinLauncher.exe --trace` → 打点 + Qt/QML 警告写入 `<exe目录>\winlauncher.trace` |

## 5. 构建产物与 VS Code 配置

### 5.1 为什么是 `build/Debug` + `build/Release`

**Ninja 是单配置生成器**：`CMAKE_BUILD_TYPE` 是「这个构建目录的编译选项」，不是目录层级。
所以「一个目录同时放 Debug/Release」这件事，单配置生成器做不到 —— 必须每配置一个目录。

| 生成器 | 产物位置 | 切配置的代价 |
|---|---|---|
| **Ninja（当前）** | `build\Debug\`、`build\Release\`（各一个目录） | 各配置缓存独立，首次各建一次，之后切换是瞬时的 |
| Ninja Multi-Config | `build\Debug\`、`build\Release\`（同一目录下） | 改配置不用重跑 configure，但首次要建两遍 |
| Visual Studio 17 2022 | `build\Debug\`、`build\Release\`（同一目录下） | 最慢，但和 VS 工程一致 |

> 说明：早期版本是 `-B build`，所以产物直接躺在 `build\WinLauncher.exe`（只有一种配置）。
> 现在 `scripts/build.bat <Debug|Release>` 把构建目录写成 `build\<Config>`，布局与习惯一致。
> 想改成「一个目录两配置」：把 kit 换成 `Ninja Multi-Config`（`.vscode/cmake-kits.json` 里已备好），
> 构建改 `cmake --build build --config <Config>`。

```bat
build.bat              :: Release（默认，含 windeployqt）
build.bat Debug        :: Debug
build.bat both         :: 两个都来
packaging\deploy.bat   :: 只重跑 windeployqt
```

构建末尾会把 `third_party\everything\Everything64.dll` 拷到 `build\<Config>\`，
所以「全盘」搜索源开箱可用；没取回 SDK 时只打一行 note，不影响构建。

### 5.2 VS Code 里的 MSVC2022 kit（为什么之前不显示）

三个原因叠加，都已修掉：

| # | 原因 | 处理 |
|---|---|---|
| 1 | **`theqtcompany.qt-cpp` 没装**。只装了 qt-core / qt-qml。kit 选择器由 **qt-cpp** 提供，缺它就没有 kit 列表 | 已 `code --install-extension theqtcompany.qt-cpp`（v1.16.0） |
| 2 | 全局 `settings.json` 里 **`"cmake.generator": "MinGW Makefiles"`**。这把 CMake Tools 钉死在 MinGW 系，MSVC / Ninja kit 会被隐藏 | 项目 `.vscode/settings.json` 覆盖为 `"Ninja"`（没动全局设置） |
| 3 | **Qt 装在非默认根目录** `C:\Container\System\Library\QT`（默认扫描 `C:\Qt`），且从未登记 | `.vscode/settings.json` 设置 `qt-core.qtInstallationRoot` + `additionalQtPaths` |

补充事实（已核对）：

- 本机**没有 VS2022 完整 IDE，只有 Build Tools**：`vswhere` 只有
  `Visual Studio Build Tools 2022`（instanceId `2dc960a9`）、`VS2019 Enterprise`、`VS2019 BuildTools`。
- 所以 `.vscode/cmake-kits.json` **按 instanceId 显式声明 kit**，不赌自动探测。
- Ninja 用 Qt 自带的 `C:\Container\System\Library\QT\Tools\Ninja\ninja.exe`（本机没有 winget 的 `Links` shim，
  所以别指望裸 `ninja` 一定在 PATH 里）。

### 5.3 直接双击 exe 跑不起来 = 没做 windeploy

**症状**：双击 `build\<Config>\WinLauncher.exe` 弹「缺少 Qt6Cored.dll」之类的错误，或者一闪就没了。

**原因**：Qt 是按 DLL 方式部署的，exe 自身**不内嵌** Qt 运行时。
之前每次都靠把 `%QT_ROOT%\bin` 塞进 `PATH` 才跑起来（`scripts\run.bat` 就是干这个的，
`.vscode/launch.json` 也注入了 PATH），所以 exe 目录里只有 `Everything64.dll`，一个 Qt DLL 都没有。
实测（把 PATH 收窄到只有 System32）：

```
WinLauncher.exe: error while loading shared libraries: Qt6Cored.dll: cannot open shared object file
exit = 127
```

**修复**：`scripts\deploy.bat [Debug|Release]` —— 跑 `windeployqt` 把 Qt 运行时拷到 exe 旁，
再补上 `Everything64.dll`（windeployqt 不认识它）。

```bat
scripts\build.bat Release
scripts\deploy.bat Release     :: 之后 build\Release\WinLauncher.exe 可双击直接跑
```

注意事项：

- `windeployqt` 要加 `--qmldir <项目>\qml`，否则它扫不到 QtQuick 的 QML 导入，运行时会缺 QML 插件。
- **Debug 和 Release 的 Qt DLL 不能混**（`Qt6Cored.dll` vs `Qt6Core.dll`），
  部署哪个配置就用对应的 `--debug` / `--release`。
- 体积：Debug 目录 235MB / Release 目录 95MB（各 29 个 Qt DLL）。
- 自检 `--test-everything` 现在**不参与单实例协商**，托盘里已经常驻一个实例时也能跑，
  不会被静默吞掉。

## 7. 实测踩坑记录（重要，别再踩）

### 7.1 运行时

1. **扫描不能放工作线程。**
   `IShellLink::GetIconLocation` 对目标是 shell 命名空间项（UWP / `AppsFolder`）的快捷方式会在 shell32 内部直接段错误（Win11 + SDK 10.0.26100 实测，第一个文件正是 `LiveCaptions.lnk`）。
   → 现状：**不调用 `GetIconLocation`**，图标统一由 `目标文件 → 快捷方式本身` 取。
   → 现状：扫描改回 **GUI 主线程分片执行**（每片 25ms 后 `QTimer::singleShot(0)` 让出），既避开 STA/线程池问题又保持 UI 跟手，顺带能显示「扫描 120/407」进度。
2. **`CoInitializeEx` / `CoUninitialize` 必须配对。** 线程池线程可能已被别人初始化；`RPC_E_CHANGED_MODE` 时调用 `CoUninitialize` 会破坏进程 COM 状态。只在 `SUCCEEDED(hr)` 时反初始化。
3. **工作线程禁用一切 GUI 侧对象。** `QFont` / `QPixmap` / `QFileIconProvider` 依赖 GUI 线程全局状态，在工作线程里用会破坏进程（表现为之后 QML 引擎构造段错误）。`IconProvider` 用 `onGuiThread()` 显式拦截。
4. **QML 组件文件必须各自 `import` 自定义模块。**
   `LauncherPanel.qml` / `SearchBar.qml` 少了 `import WinLauncher.Core`，结果 `Ctrl` / `AppConfig` 全部静默解析失败：**字面量文本正常显示，所有绑定表达式变成空值** —— 界面看起来「渲染成功但网格空白、底部状态行消失」。
   → 已装 `qInstallMessageHandler`，QML 绑定错误会写进 `--trace` 文件。
5. **shell 的 jumbo 图标列表里有些条目只是把小图标塞在左上角** → `IconProvider::normalizeIcon` 检测非透明包围盒，没铺满就裁剪放大居中。

### 7.2 工具链 / 环境

6. **`vcvars64.bat` 会调用被安全策略拦截的 `reg.exe`**，导致 Windows SDK 路径没配好（`rc.exe` / `mt.exe` 找不到）→ `scripts/build.bat` 手工拼 `PATH/INCLUDE/LIB/VCToolsInstallDir/WindowsSdkDir`。
7. **`.bat` 必须 CRLF 换行**；且不要用 `if ( ... )` 块包住含 `(x86)` 的路径 —— `%MSVC_ROOT%` 展开出的 `)` 会提前闭合代码块。改用 `if ... goto :label`。
9. **增量改头文件后 `qmltyperegistrar` 偶尔先失败一次**（报错指向 `winlauncher_qmltyperegistrations.cpp`），
   直接重跑一次 `build.bat` 就好；别为此去清 build 目录。build.bat 失败时会提示这一点。

### 7.3 玻璃、圆角、阴影：全部自绘（不再用 DWM 材质）

**为什么放弃系统材质**

原来走 `SetWindowCompositionAttribute` + `ACCENT_ENABLE_ACRYLICBLURBEHIND`，
有三个绕不过去的问题：

1. 它是 Win10 1803 时代的实现，Win11 上噪点明显、模糊半径偏小、还自带一层灰调，
   和 macOS 的 vibrancy（大半径、干净、高饱和）气质差很远；
2. **它由 DWM 按「矩形」合成，`SetWindowRgn` 裁不到它** —— 窗口区域被裁成圆角，
   材质却仍是直角，四个角上露出一块方方正正的玻璃。这就是「圆角不生效」；
3. 无边框 + 逐像素透明的窗口拿不到 DWM 的原生外阴影，面板贴不出「浮起来」的层次。

**现在的做法**（`inc/BackdropBlur.h` + `src/BackdropBlur.cpp`）

弹出前（窗口还隐藏着的时候）跑一遍：

```
BitBlt 抓窗口那块桌面像素（物理像素，只抓需要的区域）
  → 降采样 4 倍 + 3 次 box blur（前缀和实现，近似高斯，半径 36px）
  → 饱和度 ×1.6（对应 macOS 的 backdrop-filter: blur() saturate()）
  → 圆角蒙版乘 alpha（面板圆角 26px）
  → 叠一层「偏移后的圆角矩形 → 模糊」当外阴影（blur 20px / offset 8px / α 100）
  → 最外圈 6px alpha 渐隐
```

整张图经 `image://wlbg/panel?<token>` 交给 QML 铺满窗口。
QImage 没法画「超出窗口边界」的阴影，所以窗口本身比可见面板四周各大 72px，那圈就是给阴影的。

**四组必须记住的配套关系**

| 约束 | 原因 |
|---|---|
| `kShadowMargin ≥ 3×shadowBlurPx + offset`（当前 72 ≥ 3×20+8） | 阴影可见扩散约 ±3σ，边距不够就被窗口边界一刀切平，露出直角 |
| QML 面板的 `cornerRadius` 必须等于 `LauncherWindow.cornerRadius` | 底图就是按这个半径裁的，对不上会露边 |
| 阴影层不用挖掉面板区域 | 合成用 `DestinationOver`，面板区目标 alpha=255，公式会自动吃掉阴影 |
| 抓屏只能在 `show()` 之前 | 之后抓就会把自己上一帧抓进去 |

**踩到的三个坑**

11. **`QPainter::CompositionMode_DestinationIn` + `fillPath` 在这个 Qt 版本上整个不生效**
    —— 面板外 alpha 依然是 255，于是窗口整个边距区被不透明像素填满，表现出来就是
    「圆角外面套了个直角矩形」；而且肉眼分不清是底图错了还是窗口错了。
    改成「画一张圆角蒙版（普通 SourceOver 在透明底上刷白，这个组合是稳的）+ 手工乘 alpha」。
    诊断手段：把底图 dump 成 PNG 再逐点看 RGBA（`WINLAUNCHER_DUMP_BACKDROP=1`）。
12. **Qt 的逻辑坐标 × dpr ≠ 物理坐标。** 副屏（dpr=2）上算出来的抓屏区域直接越界，
    抓屏失败、底图退化成纯色；根源是每块屏的物理原点 Qt 没有暴露。
    改成完全绕开换算：用 `GetWindowRect` 直接拿窗口的**物理**矩形。
13. **抓屏别抓整块虚拟桌面。** 双屏下虚拟桌面 4800×2200，`BitBlt` + `GetDIBits` 要搬
    1000 万像素，成了整个底图生成耗时的绝大部分（137ms → 只抓目标区域后 ~50ms）。


### 7.4 Everything「全盘」搜索源（已打通）

**踩的坑：Everything 本体安装目录里没有 SDK DLL。** 实测 `C:\Program Files\Everything\` 只有
`Everything.exe` / `Everything.lng` / `Everything.ini` / `Uninstall.exe`，**没有 `Everything64.dll`**，
全盘也找不到 `es.exe`；而 `everythingsearch.cpp` 正是按 `LoadLibraryW("Everything64.dll")` 写的。
（另两条备选：② 改用 `es.exe` 走 `QProcess`；③ 开 Everything 的 HTTP Server 走 `127.0.0.1`
—— 当前 `%APPDATA%\Everything\Everything.ini` 里 `http_server_enabled=0`。**本次选了 ①**。）

**做法**

1. `scripts\fetch-everything-sdk.bat`：用 Windows 自带 `curl` + `tar` 拉
   <https://www.voidtools.com/Everything-SDK.zip>，解出 `dll/Everything64.dll` 到 `third_party\everything\`。
   DLL 是二进制、**不入库**（`.gitignore` 已排除），仓库里只放 README + 取回脚本。
2. `scripts\build.bat` 构建末尾自动把它拷到 `build\<Config>\`（exe 同目录）；
   没取回 SDK 时只打一行 note，不影响构建。
3. `EverythingSearch::probe()` 按顺序找 DLL：exe 同目录 → `C:\Program Files\Everything\`
   → `C:\Program Files (x86)\Everything\`。手动丢进 Everything 安装目录也能用。
4. 查询链：`Everything_SetSearchW` → `Everything_SetMatchCase(FALSE)` / `SetMatchPath(FALSE)` / `SetRegex(FALSE)`
   → `SetRequestFlags(FULL_PATH_AND_FILE_NAME)` → `SetMax(limit)` → `Everything_QueryW(TRUE)`（同步，
   内部泵消息）→ `Everything_GetResultFullPathNameW` 逐条取全路径；析构时 `Everything_CleanUp` + `FreeLibrary`。
5. 类型过滤按 Everything 的 `ext:` 语法拼进查询：`<关键词> ext:exe;lnk;url;bat;cmd`，
   让索引侧先筛，UI 侧再按 `.exe/.lnk/.url` 兜一道。

**实测**（本机 Everything 服务 + 控制台实例都在跑）

| 检查 | 结果 |
|---|---|
| DLL 加载 | `everything.available = true`，`loadedPath = Everything64.dll`（exe 同目录） |
| 自检 `--test-everything chrome` | `hits = 17`，返回项全是 `.exe` / `.lnk`（类型过滤生效） |
| UI 端到端 | 搜索框输入 `chrome` + 「全盘」档高亮 → 网格过滤出 2 个本机条目，下方「全盘搜索（Everything）」条带列出 16 个索引命中 |

排查入口：`WinLauncher.exe --test-everything <关键词>`（不建窗口，打印命中路径后退出）。
Everything 没跑或 DLL 缺失时 `isAvailable() == false`，自动回退本地过滤，不会报错。

### 7.5 扫描过滤与网格密度

14. **默认屏蔽「卸载类」条目。** Windows 的开始菜单和注册表里这类东西极多：每个装过的
    驱动都会留下一条 `Windows Driver Package - XXX`，每个软件都有 `Uninstall` 快捷方式。
    过滤规则（`AppScanner.cpp`）：
    - 名字含 `uninstall / unins / 卸载 / 移除 / 删除 / repair / 修复 / windows driver package /
      驱动程序包 / update for / security update / hotfix`；
    - 注册表项带 `ParentKeyName` 或 `ReleaseType`（= 某软件的子组件或系统补丁）；
    - **目标不是可执行文件**（`.pdf` / `.chm` / `.html` / `.txt`）—— 开始菜单里大量
      「用户手册」快捷方式就是这么混进来的，之前列表里出现 PDF 图标就是这条；
    - **网站快捷方式 `.url`**（→ 官网 / 文档 / 支持论坛 / `mailto:`）——
      开始菜单里每个软件都附带一堆，打开就是网页，`buildTasks` 阶段就不收。

    实测 331 → **222** 项。其中 64 个是「用户手册」类（目标 `.html` / `.chm`），
    19 个是网站快捷方式。剩下的非 exe 只有 10 个：9 个 `.msc`（Windows 管理工具：
    服务 / 事件查看器 / 任务计划程序 / 性能监视器…）和 1 个 `.bat`（Arm 工具链的
    GCC Command Prompt）—— 这些确实能启动，保留。

    排查入口：`WinLauncher.exe --dump-apps` 同步跑一遍扫描，把**最终收录**的清单写成
    `winlauncher.apps.txt`（类型 / 名字 / 目标 / 来源）。核过滤规则时比盯着 UI 数格子直接得多。

15. **网格 7 列 × 4 行**，对齐 macOS 26/27 的 Applications 面板。`cellHeight` 取容器高度
    的 1/4 并向下取整，静止时一屏正好 4 行；**滚动是自由的**（不做按行吸附、不锁位置）。
    注意 macOS 那边是**纵向滚动的分组列表，不是横向翻页**，所以这里也没有底部圆点。

**还没做**：同一软件多个入口（例如 MSYS2 的 CLANG64 / MINGW64 / MSYS / UCRT64 五个环境）
现在是逐个平铺。可行做法是「同一个开始菜单子文件夹下有 ≥3 个快捷方式就显示成一个文件夹」
（与 Windows 开始菜单的组织方式一致，数据现成、不误伤）；单纯「只显示一个」会丢启动入口。

### 7.6 应用分类 + 图标右键菜单

16. **顶部分类标签条**（对齐 macOS Applications 面板那一排 Social / Creativity / …）。

    Windows **没有** App Store 那种 category 元数据，只能按「名字 + 目标路径」做关键词匹配，
    规则集中在 `inc/AppCategory.h` / `src/AppCategory.cpp`，**顺序即优先级**
    （开发 > 影音 > 办公 > 网络 > 工具，先命中先赢）。本机实测分布：
    dev 152 / utility 66 / internet 30 / office 20 / media 10 / other 14。

    几个必须记住的点：

    - **「工具」放最后**：它的关键词最泛（driver / 管理 / 助手），放前面会吃掉一大片；
    - **「办公」要在「网络」前**：微信输入法得靠 office 的「输入法」先命中 ——
      所以 office 里写的是「输入法」而不是「微信」，否则会被 internet 的「微信」抢走；
    - **「影音」要在「网络」前**：QQ音乐含 "qq"，不能因为 "qq" 归到网络；
    - **`\qt\` 是按目标路径匹配的**：`Qt 5.15.2 (MSVC 2019 32-bit)` 这种条目名字里没有
      可用的分类线索，只有 target 路径里带；
    - **`accessibility` / `administrative` 是按开始菜单文件夹名匹配的** ——
      一次盖住辅助功能 5 个（放大镜/讲述人/屏幕键盘…）+ 管理工具一整夹。

    排查入口：`WinLauncher.exe --dump-apps` 现在多输出一列分类，改完规则跑一次就能看分布。

17. **图标右键菜单**：打开 / 以管理员身份打开 / 打开文件所在位置 / 从启动台移除。

    - 提权走 `ShellExecuteExW` + `"runas"`；`ERROR_CANCELLED` 要单独识别成「已取消提权」——
      那是用户点了 UAC 的「否」，不是错误；
    - 定位文件走 **`SHOpenFolderAndSelectItems`**，不是 `explorer /select` ——
      后者要自己拼引号，路径带空格 / 逗号时容易翻车；
    - 「从启动台移除」**只把 id 记进 `layout.json` 的 `hidden` 名单**，不删文件、不删条目，
      所以是可恢复的（设置窗口里有「全部恢复」）。扫描出来的条目尤其不能真删 ——
      下次扫描它又回来了。

**还没做（下一优先）：同源多入口归组。** 本机 J-Link 一家就占了 **37 个图标**
（V6.50a + V7.98b 两个版本各 20 多个工具），再加 MSYS2 5 个、NI 7 个 ——
逐条平铺没法看。可行做法是按开始菜单的子文件夹归组（≥3 个就折叠成一个可点开的文件夹），
数据现成（快捷方式的目录结构就是开始菜单的文件夹），也不误伤。

18. **「卸载此程序」走注册表的 `UninstallString`，没有接 Geek Uninstaller。**

    先查证过 Geek：翻它的 `geek.exe` 字符串表，里面只有 `GetCommandLineA/W` /
    `CommandLineToArgvW` 这种 CRT 标配，**没有任何命令行实现**；官网也只提供一个单文件 exe，
    **没有 DLL / SDK** —— 只能人肉点 UI，没法被程序调用。
    （它字符串里倒是藏着 `crystalidea.com/uninstall-tool?source=geek`，在推自家另一个
    有命令行的付费产品 Uninstall Tool。）

    所以改成读 Windows 自己的注册表卸载项再执行：

    - **匹配顺序**：DisplayIcon == 目标 exe → 目标在 InstallLocation 里 →
      **目标在 DisplayIcon 所在目录里** → DisplayName 全等 → DisplayName 包含 →
      去掉尾部括号再包含一次；
    - 中间那条「用 DisplayIcon 反推安装目录」是必需的：**Git for Windows 的卸载项
      压根没有 InstallLocation**，只靠前两条匹配不到 `git-bash.exe`；
    - `UninstallString` 有两种形态（`"C:\...\unins000.exe" /S` 与 `MsiExec.exe /X{GUID}`），
      得用 `CommandLineToArgvW` 拆成 exe + 参数再交给 ShellExecute —— 整串塞 lpFile 不行；
    - 用 `"open"` 而不是 `"runas"`：卸载器自己的 manifest 需要管理员时系统会自己弹 UAC，
      硬加 runas 会让 per-user 安装的程序白弹一次提权；
    - **找不到卸载项时只提示，不去强删文件** —— 强删是另一码事，风险大得多。

    查证入口：`WinLauncher.exe --test-uninstall <名字或 exe 路径>`（只打印匹配结果，不卸载）。
    实测：Git（按 git-bash.exe 路径）/ 7-Zip / MSYS2 / Everything / Python 3.12 都能正确匹配。
